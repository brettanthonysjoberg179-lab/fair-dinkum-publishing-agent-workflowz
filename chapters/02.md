# Chapter 2: Meet Your 15-Skill AI Workforce

*The agent model explained in plain English, the team roster, and why specialists beat generalists.*

---

## The factory metaphor

If you’ve ever walked through a modern manufacturing plant, you know that no single worker does everything. There are welders, painters, assemblers, quality inspectors, logistics coordinators, and floor managers. Each has a specific role, a specific toolset, and a specific output. When the system works, the car (or the microchip, or the frozen meal) moves from station to station and emerges finished.

AI agents work the same way. A generalist AI — ChatGPT, Claude, Gemini — is like a talented temp who can do many tasks but isn’t specialised for any of them. Ask it to write a chapter, and it might forget your tone guidelines. Ask it to format an ebook, and it might hallucinate a CSS rule. Ask it to do both in the same session, and you get inconsistent output.

Specialist agents are different. Each one is built for one job. The Manuscript Author doesn’t worry about Stripe webhooks. The Fact-Checker doesn’t design covers. The Launch Strategist doesn’t edit prose. This separation of concerns makes the pipeline predictable, testable, and improvable.

In this chapter, we’ll meet all fifteen agents, understand their interfaces, and see how they chain together.

---

## The base agent: shared DNA

Every agent in the workforce inherits from `BaseAgent`. This parent class provides common behaviour so the specialists can focus on their actual jobs.

**Project context**
Every agent receives a `project_id` on construction. That ID links it to a database record that stores the manuscript, outline, research notes, and artifacts. The agent never has to ask “which project am I working on?” — it knows.

**Logging**
Every agent writes structured logs. When something goes wrong, you can trace exactly which agent failed, what input it received, and what output it produced.

**Error handling**
Agents don’t crash the pipeline. They return structured error responses that the workflow service can catch, retry, or escalate to a human.

**Extensibility**
When you want to add a new agent, you inherit from `BaseAgent`, implement the `execute()` method, and register it in the workflow service. You don’t rewrite the whole system.

The base agent is the skeleton. The specialists are the organs.

## The team roster

### 1. Product Director
**Role:** Project lead and coordinator
**Input:** Project brief, niche, target audience
**Output:** Project plan, milestone list, agent dispatch schedule
**Why it exists:** Without someone setting scope and tracking progress, the other agents work in chaos. The Product Director ensures the manuscript matches the outline, the cover matches the positioning, and the sales copy matches the manuscript.

**Real-world analogy:** A film director who doesn’t act or operate the camera but makes sure every department delivers something that fits the final cut.

---

### 2. Market Researcher
**Role:** Niche intelligence and keyword analysis
**Input:** Broad topic or niche area
**Output:** Keyword list, competitor summary, audience signals, platform trends
**Why it exists:** Authors guess what readers want, and they’re usually wrong. The Market Researcher turns intuition into data. It finds the specific subtopics people search for, the gaps in existing books, and the language the audience uses.

**Real-world analogy:** A mining geologist who surveys the land before the miners move in. The minerals are the keywords; the geologist tells you where to dig.

---

### 3. Opportunity Scorer
**Role:** Niche ranking and go/no-go recommendation
**Input:** Research data, scoring weights
**Output:** Ranked niche list with scores for demand, competition, monetisation fit, and production effort
**Why it exists:** You might have five viable niche ideas. The Opportunity Scorer tells you which one to start with. It removes ego from the decision and replaces it with a repeatable model.

**Real-world analogy:** A talent scout who watches fifty players and recommends the one most likely to succeed in your system.

---

### 4. Positioning Strategist
**Role:** Differentiation and value proposition
**Input:** Niche, audience data, competitor analysis
**Output:** One-sentence hook, three-pillar value proposition, tone guidelines, audience avatar
**Why it exists:** Fifty books exist on Australian native plants. Yours needs a reason to exist beyond “I wrote another one.” Positioning finds the angle — backyard growers, restoration professionals, school teachers — and locks the tone.

**Real-world analogy:** A brand strategist who helps a new coffee shop decide whether it’s the affordable commuter spot, the premium single-origin experience, or the community hub.

---

### 5. Outline Architect
**Role:** Structural blueprint for the manuscript
**Input:** Positioning data, research notes, target length
**Output:** Hierarchical outline with parts, chapters, sections, and key takeaways
**Why it exists:** Writing without an outline is like building a house without a plan. The Outline Architect ensures logical flow, appropriate pacing, and coverage of all key points. The Manuscript Author just follows the blueprint.

**Real-world analogy:** An architect who draws the blueprints. The builder (Manuscript Author) doesn’t decide where the walls go.

---

### 6. Manuscript Author
**Role:** Long-form content generation
**Input:** Outline, research notes, positioning data, tone guidelines
**Output:** Draft chapters in Markdown
**Why it exists:** This is the workforce’s writer. It takes the structure and fills it with prose. In production, you connect this agent to a local LLM through LM Studio or an API. The agent handles prompt construction, context management, and chapter-by-chapter generation.

**Real-world analogy:** A copywriter who receives a detailed brief and returns draft copy. They don’t set strategy; they execute the plan.

---

### 7. Editor
**Role:** Polish and consistency review
**Input:** Draft manuscript, positioning data, style guide
**Output:** Revised manuscript with notes, or a list of issues for human review
**Why it exists:** First drafts are messy. The Editor catches repetition, weak transitions, tone drift, and passages that don’t match the positioning. It doesn’t rewrite creatively — it refines what’s there.

**Real-world analogy:** A sub-editor at a publishing house who marks up the manuscript before it goes to the author for final approval.

---

### 8. Fact-Checker
**Role:** Accuracy and compliance verification
**Input:** Manuscript, research sources, compliance checklist
**Output:** Verification report with flagged claims, corrections, and source citations
**Why it exists:** Nonfiction lives or dies by accuracy. The Fact-Checker verifies dates, names, statistics, regulatory references, and cultural protocols. For Australian content, this includes state-specific legislation, First Nations attribution, and biosecurity rules.

**Real-world analogy:** A legal researcher who checks that a published article doesn’t contain libellous or incorrect statements.

---

### 9. Cover Creative Director
**Role:** Visual identity and cover brief
**Input:** Title, positioning data, genre conventions, platform specs
**Output:** Cover brief, style keywords, colour palette, typography notes, image generation prompts
**Why it exists:** Readers judge books by covers. This agent doesn’t necessarily generate the final image — it produces the specification that a designer or image generation tool can execute. The brief ensures the cover matches the positioning and meets Amazon, Apple Books, and Kobo requirements.

**Real-world analogy:** An art director who sketches the concept and writes the designer’s notes, but doesn’t necessarily paint the cover themselves.

---

### 10. Production Lead
**Role:** Final file assembly and formatting
**Input:** Final manuscript, cover asset, metadata
**Output:** EPUB, PDF, and Kindle-ready files with embedded metadata and table of contents
**Why it exists:** A manuscript is not an ebook. The Production Lead handles the messy details: file formats, embedded fonts, hyperlinked tables of contents, ISBN placement, and platform-specific quirks.

**Real-world analogy:** A prepress technician who takes the designer’s files and the editor’s final copy and produces the print-ready PDF.

---

### 11. Sales Copywriter
**Role:** Marketing copy and packaging
**Input:** Manuscript summary, positioning data, competitor blurbs
**Output:** Amazon description, back-cover blurb, bullet points, author bio, series description
**Why it exists:** The best ebook in the world won’t sell if the description is boring. The Sales Copywriter writes the words that convert browsers into buyers. It studies competitor copy, tests angles, and produces platform-ready text.

**Real-world analogy:** A direct-response copywriter who writes the product page that makes someone click “Buy Now.”

---

### 12. Funnel Builder
**Role:** Sales infrastructure and delivery automation
**Input:** Sales copy, pricing, Stripe config
**Output:** Landing page copy, email sequences, payment link, tokenized download page, webhook handlers
**Why it exists:** You need a place to sell the book and a way to deliver it. The Funnel Builder creates the assets and configuration for a complete sales funnel: a simple landing page, a Stripe checkout session, a tokenized download link that expires after 72 hours, and the webhook logic that updates customer status.

**Real-world analogy:** A systems integrator who wires together the payment processor, the download server, and the email responder so the customer gets what they paid for without manual intervention.

---

### 13. Analytics Optimiser
**Role:** Performance tracking and optimisation
**Input:** Sales data, funnel metrics, customer feedback
**Output:** Revenue reports, A/B test recommendations, churn analysis
**Why it exists:** Publishing isn’t a one-and-done event. The Analytics Optimiser tracks what’s working, flags underperforming titles, suggests price changes, and recommends new angles based on actual customer behaviour.

**Real-world analogy:** A business analyst who reads the spreadsheet and tells the team which products to double down on.

---

### 14. Obsidian Knowledge Manager
**Role:** Vault publishing and knowledge management
**Input:** Research notes, outlines, draft chapters, fact-check reports
**Output:** Markdown files in an Obsidian vault with tags, links, and folder structure
**Why it exists:** Your research and drafts are valuable assets beyond a single ebook. The Knowledge Manager publishes them to an Obsidian vault so you can cross-link ideas, reuse content, and build a personal knowledge base that grows with every project.

**Real-world analogy:** A librarian who catalogs the research so the next author on the team can find it instantly.

---

### 15. Launch Strategist
**Role:** Release planning and first-week promotion
**Input:** Final ebook, sales assets, pricing, target audience
**Output:** Release calendar, platform checklist, email sequence, social media posts, early-reviewer list
**Why it exists:** A book that launches invisibly sells invisibly. The Launch Strategist plans the first week: which platforms get the book, who receives advance copies, what emails go out when, and how to turn launch momentum into ongoing sales.

**Real-world analogy:** A publicist who coordinates the book tour, the press releases, and the launch party.

## How agents communicate

Agents don’t pass messages by yelling across the room. They pass data through the project database. Here’s the flow:

1. **Product Director** creates a project record with status `briefed`.
2. **Market Researcher** saves keyword and competitor data to the `opportunity` table.
3. **Opportunity Scorer** reads that data, calculates scores, and updates the project with `positioning_ready`.
4. **Positioning Strategist** writes the positioning statement and updates the project with `outline_ready`.
5. **Outline Architect** builds the outline and saves chapters to the `outline` and `chapter` tables.
6. **Manuscript Author** reads the outline, writes sections, and saves them to the `manuscript` and `section` tables.
7. **Editor** and **Fact-Checker** read the manuscript, add notes, and update status to `polished`.
8. **Cover Creative Director** saves the brief and generated assets to the `artifact` table.
9. **Production Lead** assembles the final files and updates `ebook_path`.
10. **Sales Copywriter** saves copy to the `artifact` table.
11. **Funnel Builder** creates the Stripe products and saves the checkout URL to `stripe_payment_link`.
12. **Analytics Optimiser** reads sales data and produces optimisation reports.
13. **Obsidian Knowledge Manager** publishes research and drafts to the vault.
14. **Launch Strategist** coordinates the release and updates the project status to `launched`.

The workflow service (`app/services/workflow.py`) runs this sequence. It calls each agent’s `execute()` method, passes the project ID, and checks the returned status. If an agent returns an error, the workflow pauses and waits for human intervention.

## Why fifteen and not three

You could ask: why not one “super agent” that does everything? The answer is reliability, testability, and cost.

**Reliability:** When one agent has one job, it’s easier to make it good. The Fact-Checker doesn’t need to know how to write a cover brief. It just needs to verify claims. Narrow scope means fewer failure modes.

**Testability:** You can write a test for the Fact-Checker that gives it a manuscript with a deliberate error and checks that it flags it. You can’t write that test if the Fact-Checker is bundled inside a generalist that also writes poetry.

**Cost:** Local LLMs have limited context windows. An agent that handles only one task needs a smaller prompt and produces smaller outputs. That means faster inference, lower memory usage, and cheaper API bills if you’re using a cloud model.

**Maintainability:** When you want to improve the Editor, you change one file. You don’t risk breaking the Sales Copywriter or the Outline Architect.

Fifteen agents sounds like a lot. In practice, it’s just a clean folder structure and a consistent interface. You can start with five agents and add the rest as you need them.

## The agent interface contract

Every agent implements the same `execute()` signature. This consistency is what makes the pipeline work.

```python
def execute(self, **kwargs) -> dict:
    """
    Run the agent's core logic.
    
    Returns a dict with at least:
    - status: "success" or "error"
    - message: human-readable summary
    - data: optional structured result
    """
```

The workflow service doesn’t need to know what each agent does internally. It just calls `execute()`, checks the `status`, and moves to the next agent. This is the open/closed principle: open for extension, closed for modification. You can add new agents without changing the workflow engine.

## Running the workforce locally

Before we build each agent in detail, let’s see the whole team in action. The project includes a test suite that exercises the workflow service. You don’t need to write any code yet.

```bash
cd ~/fair-dinkum-publishing-agent-workforce
python3 -m pytest tests/test_workflow.py -v
```

This runs through the full pipeline in mock mode. Each agent receives test data, processes it, and returns a result. You’ll see the project status transition from `briefed` to `launched`. If any agent fails, the test stops and reports the error.

This is your safety net. As you modify agents, the tests tell you whether you broke something.

## The mock vs live decision

By default, the agents run in mock mode. They return simulated data without calling external APIs. This is intentional. You should understand the workflow, verify the tests pass, and only then connect live services.

When you’re ready to go live, you change environment variables:

```bash
export LLM_PROVIDER=lmstudio
export LLM_BASE_URL=http://localhost:1234/v1
export LLM_API_KEY=lm-studio
export STRIPE_SECRET_KEY=sk_live_...
export STRIPE_WEBHOOK_SECRET=whsec_...
export OBSIDIAN_VAULT_PATH=$HOME/Documents/Obsidian\ Vault
```

The agents detect these variables and switch from mock to live execution. The interface doesn’t change. The output format doesn’t change. Only the internal implementation changes.

This is one of the most important design decisions in the workforce. You can develop and test without spending money on API calls, then flip a switch to production.

## Customising the team

You don’t have to use all fifteen agents. If you’re writing fiction, you might skip the Fact-Checker and add a Sensitivity Reader. If you’re publishing technical documentation, you might add a Code Example Validator. If you’re building a series, you might add a Series Continuity Checker.

The agent system is designed to be modular. Add new agents by creating a new file in `app/agents/`, inheriting from `BaseAgent`, and adding the agent name to the valid list in `app/api/routes.py`. That’s it.
