## The security mindset

Security isn't a feature you add at the end — it's a discipline you practice from day one. The Fair Dinkum workforce handles customer payments, personal data, and proprietary content. A breach in any of these would be catastrophic.

This chapter covers the security measures built into the workforce, not as an afterthought, but as foundational architecture.

## Secrets management

### The golden rule

Secrets never appear in source code, configuration files, or logs. Ever. Not even in comments. Not even in example files with placeholder text like "sk_live_***".

### How secrets flow

```
Secret vault (Docker secrets / CI secrets / local .env)
    ↓
Environment variable at runtime
    ↓
Application reads from os.environ
    ↓
Never logged, never serialised, never persisted
```

### Secret rotation

```bash
# Rotate Stripe secret key
stripe secret rotate --name production

# Update Docker secret
echo "new_secret" | docker secret create stripe_secret_key_new -
docker service update --secret-rm stripe_secret_key_old --secret-add src=stripe_secret_key_new,target=stripe_secret_key api
```

Rotate keys on any suspected compromise and annually as a matter of policy.

## Stripe webhook verification

Webhooks are a common attack vector — anyone can POST to your endpoint pretending to be Stripe. Verification is non-negotiable:

```python
import stripe
from fastapi import Request, HTTPException

async def handle_stripe_webhook(request: Request):
    payload = await request.body()
    sig_header = request.headers.get("stripe-signature")
    
    try:
        event = stripe.Webhook.construct_event(
            payload, sig_header, webhook_secret
        )
    except ValueError:
        raise HTTPException(status_code=400, detail="Invalid payload")
    except stripe.error.SignatureVerificationError:
        raise HTTPException(status_code=400, detail="Invalid signature")
    
    # Process the verified event
    await process_event(event)
```

### Why this matters

Without verification, an attacker could:

- Mark unpaid invoices as paid
- Trigger fake subscription cancellations
- Generate fraudulent download links
- Access customer email addresses

The signature verification ensures the webhook actually came from Stripe and wasn't modified in transit.

## SQL injection prevention

SQL injection remains one of the most common web application vulnerabilities. SQLAlchemy's ORM and parameterised queries provide strong defence:

### Safe (ORM)

```python
# SQLAlchemy automatically parameterises
project = session.query(Project).filter(Project.id == project_id).first()
```

### Safe (Core with parameters)

```python
from sqlalchemy import text

result = session.execute(
    text("SELECT * FROM projects WHERE id = :id"),
    {"id": project_id}
)
```

### Unsafe (never do this)

```python
# String concatenation in SQL — NEVER
result = session.execute(f"SELECT * FROM projects WHERE id = '{project_id}'")
```

If an attacker controls `project_id`, they could inject SQL like `' OR 1=1; DROP TABLE projects; --`. SQLAlchemy's parameterisation makes this impossible.

## Cross-site scripting (XSS)

The API doesn't render HTML directly, but any user-generated content served to browsers needs sanitisation:

```python
import bleach

def sanitize_html(content: str) -> str:
    return bleach.clean(
        content,
        tags=["p", "br", "strong", "em", "ul", "ol", "li", "a", "h1", "h2", "h3"],
        attributes={"a": ["href", "title"]},
        strip=True
    )
```

## Cross-origin resource sharing (CORS)

The API only accepts requests from approved origins:

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "https://fairdinkum.com",
        "https://www.fairdinkum.com",
    ],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)
```

Requests from other origins are rejected by the browser. This prevents malicious websites from making authenticated requests on behalf of logged-in users.

## Rate limiting

Rate limiting prevents abuse of expensive endpoints:

```python
from fastapi import Request, HTTPException
from datetime import datetime, timedelta

class RateLimiter:
    def __init__(self, requests_per_minute: int = 30):
        self.requests_per_minute = requests_per_minute
        self.requests: dict[str, list[datetime]] = {}
    
    async def check(self, request: Request):
        client_ip = request.client.host
        now = datetime.utcnow()
        window_start = now - timedelta(minutes=1)
        
        # Clean old entries
        if client_ip in self.requests:
            self.requests[client_ip] = [
                t for t in self.requests[client_ip] if t > window_start
            ]
        else:
            self.requests[client_ip] = []
        
        # Check limit
        if len(self.requests[client_ip]) >= self.requests_per_minute:
            raise HTTPException(status_code=429, detail="Rate limit exceeded")
        
        self.requests[client_ip].append(now)
```

Endpoints with different resource costs use different limits:

| Endpoint | Limit | Rationale |
|----------|-------|-----------|
| /health | 100/min | Cheap, health checks |
| /pipeline/start | 10/min | Expensive, agent execution |
| /webhooks/stripe | 200/min | External service |
| /download | 30/min | Token validation |

## Authentication and authorisation

### API key authentication

```python
API_KEYS = {"sk_live_***": "production", "sk_test_***": "testing"}

async def verify_api_key(request: Request):
    api_key = request.headers.get("Authorization", "").replace("Bearer ", "")
    if api_key not in API_KEYS:
        raise HTTPException(status_code=401, detail="Invalid API key")
    return API_KEYS[api_key]
```

### Role-based access control

```python
ROLES = {
    "admin": ["read", "write", "delete", "deploy"],
    "author": ["read", "write"],
    "viewer": ["read"],
}

def check_permission(role: str, permission: str):
    if permission not in ROLES.get(role, []):
        raise HTTPException(status_code=403, detail="Insufficient permissions")
```

## Australian regulatory compliance

### Australian Consumer Law (ACL)

The ebook must not make misleading claims. Specific rules:

- **No unsubstantiated results:** "Bestselling" only if it actually was. "Proven" only with evidence.
- **No fake testimonials:** All reviews must be from real buyers, unscripted.
- **Clear pricing:** Total price displayed before purchase, no hidden charges.
- **Refund policy:** Must comply with Australian consumer guarantees — if the product isn't as described, a refund is required by law.

### Privacy Act 1988

If you collect personal information (email names, purchase records):

- **Australian Privacy Principles:** Must have a privacy policy explaining what you collect and why.
- **Data minimisation:** Only collect what you need. Don't ask for phone numbers if email suffices.
- **Access and correction:** Customers can request their data be corrected or deleted.
- **Data breach notification:** If a breach is likely to cause serious harm, notify the OAIC and affected individuals.

### Spam Act 2003

Commercial email must:

- Have the recipient's consent (express or inferred)
- Include a functional unsubscribe mechanism
- Identify the sender accurately

The email sequence in Chapter 11 is designed to comply with these requirements.

## Content compliance

### Copyright

- All images used with appropriate licence or original creation
- Quotes attributed and within fair use limits
- No scraped content from competitor books

### Defamation

- No identifiable individuals portrayed negatively without evidence
- Opinions clearly labelled as opinions
- No false statements that could damage reputation

### Financial and health advice

- General information only, not personalised advice
- Disclaimers on every page with actionable advice
- No specific recommendations to buy/sell investments or follow medical treatments

## Security incident response

Despite best practices, incidents happen. The response plan:

1. **Identify:** Detect the incident through monitoring or reports
2. **Contain:** Isolate affected systems and revoke compromised credentials
3. **Eradicate:** Remove the root cause (patch vulnerability, fix configuration)
4. **Recover:** Restore affected systems and data from clean backups
5. **Learn:** Post-incident review to prevent recurrence

### Communication templates

Pre-drafted templates for common scenarios:

- Data breach notification to OAIC
- Customer notification of security incident
- Internal team communication
- Public statement if needed
