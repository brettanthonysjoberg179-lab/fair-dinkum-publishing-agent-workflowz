## The principles behind the tools

Before we install anything, let’s establish the criteria that shaped the stack. Every technology in this book was selected because it satisfies at least three of the following:

**1. Local-first**
Runs on your machine without mandatory cloud dependencies. You can develop offline, deploy offline, and recover from a service shutdown without losing your pipeline.

**2. Open source or transparent pricing**
You can inspect the code, audit the dependencies, and understand exactly what you’re paying for. No black boxes, no surprise API changes, no vendor lock-in.

**3. Australian-friendly**
Works with AUD pricing, Australian time zones, and local infrastructure. No US-centric dashboards or Northern Hemisphere payment gateways.

**4. Production-ready**
This isn’t a weekend project stack. Every tool is used in production systems today. If you outgrow the local setup, you can migrate to a hosted version without rewriting the workflow.

**5. Testable**
Every component can be exercised in isolation. You can write tests that verify the database, the API, the agents, and the Stripe integration without touching external services.

These principles are non-negotiable. If a tool doesn’t pass them, it doesn’t get into the stack.

## FastAPI: the orchestration layer

FastAPI is the web framework that powers the MCP server. It’s the interface between you, the agents, and the database.

**Why FastAPI?**
- **Native async support:** Agent execution is I/O-bound. FastAPI’s async handlers let you run multiple agents concurrently without blocking the event loop.
- **Automatic documentation:** FastAPI generates OpenAPI docs at `/docs`. You can test every endpoint from a browser without writing a frontend.
- **Type safety:** Pydantic models define request and response shapes. If an agent returns data in the wrong format, FastAPI catches it before it reaches the client.
- **Performance:** FastAPI is one of the fastest Python web frameworks. It handles concurrent requests efficiently, which matters when multiple agents hit the database simultaneously.

**What it’s not**
FastAPI isn’t a job queue. It doesn’t handle long-running tasks like writing a full manuscript in the background. For that, we use the workflow service with explicit state management. FastAPI is the controller, not the worker.

**Alternatives considered**
- **Flask:** Simpler, but async support requires extensions, and type safety is weaker. Flask is fine for small apps; FastAPI is better for an agent orchestration layer.
- **Django:** Too heavy. Django includes an ORM, admin panel, and auth system we don’t need. We already use SQLAlchemy directly.
- **FastMCP:** A specialised MCP framework. We considered it, but it abstracts away too much of the HTTP layer. For learning and debugging, explicit FastAPI routes are clearer.

## SQLAlchemy + Alembic: the database backbone

SQLAlchemy is the Python SQL toolkit and ORM. Alembic is its migration tool. Together they form the persistence layer for every project, outline, manuscript, and artifact.

**Why SQLAlchemy?**
- **Local-first by default:** SQLAlchemy works with SQLite out of the box. No database server to install, no connection strings to manage. You open a file, and you have a database.
- **Production upgrade path:** When you outgrow SQLite, SQLAlchemy supports PostgreSQL, MySQL, and others with a single line change in the connection string. You don’t rewrite your models.
- **Query flexibility:** You can write raw SQL when you need performance, or use the ORM when you need convenience. The repository layer gives you both.
- **Maturity:** SQLAlchemy has been around since 2005. It’s battle-tested, well-documented, and unlikely to disappear.

**Why Alembic?**
Schema changes happen. You add a column, rename a table, split a model. Without migrations, every team member has a slightly different database schema. Alembic tracks schema versions, generates migration scripts, and applies them in order. It’s like Git for your database.

**The local-first advantage**
Your entire project database lives in `data/app.db`. Copy that file and you’ve backed up everything: projects, outlines, manuscripts, artifacts, and research notes. No cloud sync required. No export wizard. No vendor dependency.

## Stripe: payments without the middleman

Stripe is the payment processor. It handles checkout, subscriptions, webhooks, and payouts.

**Why Stripe?**
- **Australian-friendly:** Stripe supports AUD natively, settles in Australian dollars, and handles GST through tax calculation APIs.
- **Developer experience:** The Stripe Python library is clean, well-documented, and consistent. Creating a checkout session is a single function call.
- **Webhook architecture:** Stripe’s webhook system tells you when payments succeed, subscriptions cancel, and invoices fail. You can automate the entire customer lifecycle.
- **No middleman fees:** By connecting Stripe directly, you avoid platform fees that eat into your margins. A $4.99 ebook through a typical platform might net you $3.50. Direct Stripe checkout can net you $4.70.

**The integration model**
The Stripe MCP server wraps the Stripe Python library in MCP tools. The FastAPI app exposes `/stripe/products` and `/stripe/stats` endpoints for quick integration. The Funnel Builder agent calls these endpoints to create products, generate checkout links, and verify webhooks.

**Alternatives considered**
- **PayPal:** Higher fees, worse API, clunky subscription model.
- **Square:** Good for physical goods, weaker for digital products and subscriptions.
- **Paddle:** Acts as a reseller, which adds complexity for tax and compliance.
- **Crypto:** Interesting for sovereignty, but not practical for mainstream Australian book buyers yet.

Stripe is the pragmatic choice. It’s not perfect, but it’s the best available option for digital product sales in 2026.

## Obsidian: the knowledge layer

Obsidian is a Markdown-based note-taking app. In the workforce, it serves as the publishing target for research notes, outlines, and draft chapters.

**Why Obsidian?**
- **Markdown-native:** Every agent output is Markdown. Obsidian reads it natively. No conversion, no formatting loss, no proprietary formats.
- **Local-first:** Your vault lives in a folder on your machine. You can back it up, sync it with Git, or open it in any text editor.
- **Graph view:** Obsidian’s backlinks and graph view help you see connections between research topics, ebook ideas, and customer data.
- **Plugin ecosystem:** Obsidian supports community plugins for publishing, task management, and database views. You can extend it without changing the agent code.

**The integration model**
The Obsidian Knowledge Manager agent writes Markdown files to a configurable vault path. Each project gets its own folder. Research notes, outlines, chapters, and fact-check reports are saved as individual files with YAML frontmatter for metadata. Obsidian indexes them automatically.

**Alternatives considered**
- **Notion:** Cloud-first, proprietary format, API rate limits.
- **Roam Research:** Subscription model, cloud-first, smaller user base.
- **Plain Markdown folder:** Works, but lacks the backlink graph and plugin ecosystem that make Obsidian useful for knowledge management.

## Local LLMs vs cloud APIs

The Manuscript Author, Editor, and other content agents need a language model. You have two choices: run it locally or call a cloud API.

**Local LLMs with LM Studio or Ollama**
- **Pros:** No API costs, complete privacy, offline capability, no rate limits.
- **Cons:** Requires a decent GPU, slower inference on CPU, smaller context windows for consumer hardware.
- **Best for:** Development, privacy-sensitive content, high-volume generation.

**Cloud APIs (OpenAI, Anthropic, Google)**
- **Pros:** Best-in-class quality, large context windows, no hardware requirements.
- **Cons:** Ongoing costs, data leaves your machine, rate limits, dependency on third-party availability.
- **Best for:** Production workloads where quality matters more than cost.

**The hybrid approach**
The workforce supports both. You set `LLM_PROVIDER=lmstudio` for local models or `LLM_PROVIDER=openai` for cloud APIs. The agent code doesn’t change. You flip a switch in `.env`.

For Australian creators on a budget, local LLMs through LM Studio are the default. A mid-range GPU (RTX 3060 or better) can run 7B–13B parameter models at usable speeds. For the best quality, you can pay for API calls on a per-ebook basis.

## Docker: one-command deployment

Docker packages the entire workforce — Python runtime, dependencies, database, and server — into a single container. You can move it between machines, deploy it to a VPS, or share it with collaborators without environment headaches.

**Why Docker?**
- **Consistency:** “It works on my machine” becomes “It works in the container.”
- **Isolation:** The container has its own filesystem, network, and dependencies. It doesn’t interfere with your host system.
- **Portability:** The same Docker image runs on your laptop, a dedicated server, or a cloud VPS.
- **One command startup:** `docker compose up` starts the FastAPI server, initialises the database, and runs migrations.

**The compose file**
The project includes `docker-compose.yml` with two services:
- `app`: The FastAPI MCP server
- `db`: PostgreSQL for production (SQLite is used in development)

You can switch between them by changing the `DATABASE_URL` environment variable.

## Security and secrets management

Every production system needs secrets: Stripe API keys, database passwords, webhook signatures. The workforce handles them through environment variables and `.env` files.

**The rules:**
1. Never commit secrets to Git. The `.gitignore` file blocks `.env`, `*.key`, and `data/`.
2. Use `.env.example` as a template. It shows required variables without exposing values.
3. In production, use a secrets manager or encrypted environment files.
4. Rotate Stripe webhook secrets and API keys periodically.

**Stripe webhook security**
The Stripe MCP server verifies webhook signatures using `STRIPE_WEBHOOK_SECRET`. This ensures that only Stripe can update your customer data. Never disable signature verification in production.

## Decision matrix

If you’re adapting this stack for a different use case, here’s a quick decision guide:

| Need | Choose | Alternative |
|------|--------|-------------|
| Simple local dev | SQLite | PostgreSQL |
| Production database | PostgreSQL | MySQL |
| AI inference | LM Studio local | OpenAI API |
| Payments | Stripe | Paddle (if reseller model preferred) |
| Knowledge base | Obsidian | Plain Markdown folder |
| Deployment | Docker | bare metal with systemd |
| Frontend | FastAPI docs | React, HTMX, or plain HTML |
| Queue for long jobs | asyncio + state | Celery + Redis |

The workforce is built to be swapped. Change the database, keep the agents. Change the LLM, keep the workflow. Change the payment processor, keep the funnel logic.
