# Chapter 13: Production Deployment

*Docker containerisation, environment configuration, CI/CD, logging, monitoring, and alerting.*

## The deployment gap

Building software is one thing. Running it reliably in production is another. This chapter bridges that gap — taking the Fair Dinkum Publishing workforce from a local development setup to a production deployment that runs 24/7 without constant attention.

## Docker containerisation

The entire workforce runs in Docker containers. The `docker-compose.yml` defines the full stack:

```yaml
version: "3.9"

services:
  api:
    build:
      context: .
      dockerfile: Dockerfile
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=sqlite:///data/workforce.db
      - STRIPE_SECRET_KEY=${STRIPE_SECRET_KEY}
      - STRIPE_WEBHOOK_SECRET=${STRIPE_WEBHOOK_SECRET}
      - JWT_SECRET=${JWT_SECRET}
      - LOG_LEVEL=INFO
    volumes:
      - ./data:/app/data
      - ./logs:/app/logs
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/health"]
      interval: 30s
      timeout: 10s
      retries: 3

  stripe-mcp:
    build:
      context: ./stripe-mcp-server
      dockerfile: Dockerfile
    ports:
      - "8001:8001"
    environment:
      - STRIPE_SECRET_KEY=${STRIPE_SECRET_KEY}
      - STRIPE_WEBHOOK_SECRET=${STRIPE_WEBHOOK_SECRET}
    restart: unless-stopped

  webhook-proxy:
    image: stripe/stripe-cli:latest
    command: listen --forward-to http://api:8000/webhooks/stripe
    environment:
      - STRIPE_API_KEY=${STRIPE_SECRET_KEY}
      - STRIPE_DEVICE_NAME=fair-dinkum-prod
    restart: unless-stopped
```

### Multi-stage Dockerfile

The API Dockerfile uses multi-stage builds to keep the image small:

```dockerfile
# Stage 1: Build dependencies
FROM python:3.13-slim as builder
WORKDIR /app
COPY pyproject.toml .
RUN pip install --no-cache-dir --break-system-packages -e .

# Stage 2: Production image
FROM python:3.13-slim
WORKDIR /app
COPY --from=builder /usr/local/lib/python3.13/site-packages /usr/local/lib/python3.13/site-packages
COPY . .
EXPOSE 8000
CMD ["uvicorn", "app.api.server:app", "--host", "0.0.0.0", "--port", "8000"]
```

## Environment configuration

Production configuration comes from environment variables, never from code:

```bash
# .env.production
DATABASE_URL=sqlite:///data/workforce.db
STRIPE_SECRET_KEY=sk_live_***
STRIPE_WEBHOOK_SECRET=whsec_***
JWT_SECRET=your-256-bit-secret-here
LOG_LEVEL=INFO
LOG_FORMAT=json
SENTRY_DSN=https://sentry.io/your-dsn
ALLOWED_ORIGINS=https://fairdinkum.com,https://www.fairdinkum.com
```

### Secrets management

Secrets are never committed to git. They're injected at deployment time:

```bash
# Load secrets from a secure location
export $(cat .env.production | xargs)

# Or use Docker secrets
echo "sk_live_***" | docker secret create stripe_secret_key -
```

## Database migrations

Schema changes are managed with Alembic:

```bash
# Generate a new migration
alembic revision --autogenerate -m "add customer table"

# Review the migration
cat migrations/versions/xxxx_add_customer_table.py

# Apply migrations
alembic upgrade head

# Rollback one step
alembic downgrade -1
```

### Production migration checklist

1. Backup the database before migrating
2. Run migrations in a staging environment first
3. Verify migrations apply cleanly
4. Apply to production during low-traffic hours
5. Verify application health after migration
6. Keep the rollback script ready

## CI/CD pipeline

GitHub Actions automates testing and deployment:

```yaml
name: Deploy

on:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"
      - run: pip install --break-system-packages -e ".[dev]"
      - run: pytest tests/ -v --tb=short

  deploy:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to production
        run: |
          ssh deploy@fairdinkum.com "
            cd /opt/fair-dinkum &&
            git pull origin main &&
            docker-compose -f docker-compose.prod.yml up -d --build
          "
```

## Logging

Structured logging is essential for production debugging:

```python
import structlog

logger = structlog.get_logger()

async def execute_agent(agent, context):
    logger.info(
        "agent_execution_started",
        agent=agent.name,
        project_id=context.project_id,
        phase=context.phase
    )
    try:
        result = await agent.execute(context)
        logger.info(
            "agent_execution_completed",
            agent=agent.name,
            project_id=context.project_id,
            duration=result.duration,
            artifacts_generated=len(result.artifacts)
        )
        return result
    except Exception as e:
        logger.error(
            "agent_execution_failed",
            agent=agent.name,
            project_id=context.project_id,
            error=str(e),
            exc_info=True
        )
        raise
```

### Log levels

- **DEBUG:** Detailed execution flow (development only)
- **INFO:** Agent starts, completions, state transitions
- **WARN:** Retries, slow executions, degraded performance
- **ERROR:** Failures, exceptions, data integrity issues
- **CRITICAL:** Security incidents, data loss, system unavailability

## Monitoring

Production monitoring tracks four golden signals:

### 1. Latency

How long requests take:

```
GET /health:     p50=12ms, p95=45ms, p99=89ms
POST /pipeline:  p50=2.3s, p95=8.1s, p99=15.4s
```

### 2. Traffic

Request volume over time:

```
Requests/minute: 45
Active projects:  12
Queue depth:      3
```

### 3. Errors

Failure rate by endpoint:

```
Overall error rate: 0.3%
/webhooks/stripe:   0.1%
/pipeline/start:    1.2% ← investigate
```

### 4. Saturation

Resource utilisation:

```
CPU:    34%
Memory: 2.1GB / 4GB (53%)
Disk:   12GB / 50GB (24%)
```

## Alerting

Alerts are configured for conditions that require human attention:

```yaml
alerts:
  - name: HighErrorRate
    condition: error_rate > 5% for 5 minutes
    severity: critical
    notify: [email, sms]

  - name: SlowAgentExecution
    condition: agent_duration > 300s for 3 consecutive runs
    severity: warning
    notify: [email]

  - name: DiskSpaceLow
    condition: disk_usage > 80%
    severity: warning
    notify: [email]

  - name: PaymentFailure
    condition: stripe_webhook_errors > 10 in 10 minutes
    severity: critical
    notify: [email, sms]
```

## Backup strategy

Data loss is catastrophic. The backup strategy covers three layers:

### 1. Database backups

```bash
# Daily automated backup
0 2 * * * sqlite3 /app/data/workforce.db ".backup /backups/workforce-$(date +\%Y\%m\%d).db"

# Weekly offsite sync
0 3 * * 0 aws s3 sync /backups/ s3://fairdinkum-backups/
```

### 2. Artifact storage

All generated artifacts (manuscripts, covers, EPUBs) are stored in cloud object storage with versioning enabled.

### 3. Configuration backup

Environment files, Docker compose, and deployment scripts are stored in a private GitHub repository with access logging.

## Key takeaways

- Docker containers ensure consistent runtime environments.
- Multi-stage builds keep images small and secure.
- Environment variables inject secrets at deployment time.
- Alembic manages schema migrations with rollback capability.
- CI/CD automates testing and deployment.
- Structured logging enables production debugging.
- Monitor four golden signals: latency, traffic, errors, saturation.
- Alert on conditions that require human attention.
- Backup everything: database, artifacts, and configuration.
