## The scaling challenge

Fifteen agents handle one project well. But what happens when you have ten projects running simultaneously? Or a hundred? Or when you want to add a sixteenth agent that generates audiobook scripts?

Scaling the workforce requires thinking about three dimensions:

1. **Horizontal scaling:** More projects running concurrently
2. **Vertical scaling:** More agents in the pipeline
3. **Depth scaling:** More complex individual agents

## Adding new agents

The workforce is designed for extension. Adding a new agent follows a strict protocol:

### Step 1: Define the agent contract

```python
class AudiobookScriptAgent(BaseAgent):
    name = "audiobook_script"
    version = "1.0.0"
    
    def __init__(self):
        super().__init__()
        self.input_schema = ManuscriptInput
        self.output_schema = AudiobookScriptOutput
```

### Step 2: Declare dependencies

```python
@property
def dependencies(self) -> list[str]:
    return ["manuscript_author", "editorial_agent"]
```

The new agent declares it needs the manuscript and editorial report. The workflow service ensures these complete first.

### Step 3: Implement execution

```python
async def execute(self, context: AgentContext) -> AgentResult:
    manuscript = context.artifacts["manuscript_author"]
    editorial_notes = context.artifacts["editorial_agent"]
    
    script = await self.generate_audiobook_script(
        manuscript=manuscript,
        editorial_notes=editorial_notes,
        voice_profile=context.config.get("voice_profile", "neutral_aussie")
    )
    
    return AgentResult(
        status="completed",
        artifacts={"audiobook_script": script},
        metrics={"duration": script.duration, "word_count": script.word_count}
    )
```

### Step 4: Register in the pipeline

```python
agents = [
    # ... existing 15 agents ...
    AudiobookScriptAgent(),  # new agent
]
```

The workflow service automatically detects the new agent and integrates it into the dependency graph.

### Step 5: Write tests

```python
@pytest.mark.asyncio
async def test_audiobook_script_agent():
    agent = AudiobookScriptAgent()
    context = AgentContext(
        project_id="test-123",
        artifacts={
            "manuscript_author": mock_manuscript(),
            "editorial_agent": mock_editorial_notes()
        }
    )
    
    result = await agent.execute(context)
    
    assert result.status == "completed"
    assert "audiobook_script" in result.artifacts
    assert result.artifacts["audiobook_script"].duration > 0
```

## Parallel execution

Some agents have no dependencies on each other and can run concurrently. The workflow service detects these opportunities automatically:

### Dependency graph analysis

```
ProductDirector → MarketResearcher → OpportunityScorer → PositioningStrategist
                                                        ↓
                                              ┌─────────┴─────────┐
                                              ↓                   ↓
                                    OutlineArchitect      CoverCreativeDirector
                                              ↓
                                    ManuscriptAuthor
                                              ↓
                                    EditorialAgent ← FactCheckComplianceAgent
                                              ↓
                                    EbookProductionAgent
                                              ↓
                                    SalesCopywriter ← FulfilmentAgent
                                              ↓
                                    AnalyticsOptimisationAgent
                                              ↓
                                    ObsidianKnowledgeManager
                                              ↓
                                    LaunchStrategist
```

The workflow service identifies that `CoverCreativeDirector` and `OutlineArchitect` can run in parallel after `PositioningStrategist` completes. Similarly, `SalesCopywriter` and `FulfilmentAgent` can run in parallel after `EbookProductionAgent`.

### Parallel execution implementation

```python
async def execute_parallel_group(self, agents: list[BaseAgent], context: AgentContext):
    tasks = [agent.execute(context) for agent in agents]
    results = await asyncio.gather(*tasks, return_exceptions=True)
    
    for agent, result in zip(agents, results):
        if isinstance(result, Exception):
            await self._handle_failure(agent, result, context)
        else:
            context.artifacts[agent.name] = result.artifacts
    
    return context
```

### Performance impact

Parallel execution reduces total pipeline time by 15-20% for a full 15-agent run. The savings increase as more agents are added to parallel groups.

## Queue-based architecture

For high-volume workloads, a simple in-memory queue isn't sufficient. The workforce supports pluggable queue backends:

### Local queue (default)

```python
class LocalQueue:
    """In-memory queue for single-instance deployments."""
    
    def __init__(self):
        self._queue: asyncio.Queue = asyncio.Queue()
    
    async def enqueue(self, job: PipelineJob):
        await self._queue.put(job)
    
    async def dequeue(self) -> PipelineJob:
        return await self._queue.get()
```

### Redis queue (production)

```python
class RedisQueue:
    """Redis-backed queue for multi-instance deployments."""
    
    def __init__(self, redis_url: str):
        self.redis = aioredis.from_url(redis_url)
    
    async def enqueue(self, job: PipelineJob):
        await self.redis.lpush("pipeline:queue", job.json())
    
    async def dequeue(self) -> PipelineJob:
        _, data = await self.redis.brpop("pipeline:queue", timeout=30)
        return PipelineJob.parse_raw(data)
```

### Queue workers

```python
class QueueWorker:
    def __init__(self, queue: QueueBackend, workflow_service: WorkflowService):
        self.queue = queue
        self.workflow = workflow_service
    
    async def run(self):
        while True:
            job = await self.queue.dequeue()
            asyncio.create_task(self.process_job(job))
    
    async def process_job(self, job: PipelineJob):
        try:
            result = await self.workflow.run_full_pipeline(job.project_id)
            await self.queue.ack(job, result)
        except Exception as e:
            await self.queue.nack(job, error=str(e))
```

Multiple workers can run concurrently, each processing jobs from the same queue. This scales horizontally by adding more worker instances.

## Multi-project isolation

When running multiple projects simultaneously, isolation is critical. A failure in one project must not affect others.

### Database isolation

Each project has its own database row with a unique ID. All artifacts are scoped to the project:

```python
class Project(Base):
    __tablename__ = "projects"
    
    id = Column(String, primary_key=True)
    status = Column(String, default="created")
    created_at = Column(DateTime, default=datetime.utcnow)
    updated_at = Column(DateTime, onupdate=datetime.utcnow)

class Artifact(Base):
    __tablename__ = "artifacts"
    
    id = Column(String, primary_key=True)
    project_id = Column(String, ForeignKey("projects.id"))
    agent_name = Column(String)
    data = Column(JSON)
    created_at = Column(DateTime, default=datetime.utcnow)
```

### Resource isolation

Each project runs in its own asyncio task with isolated error handling:

```python
async def run_project(self, project_id: str):
    try:
        async with self.project_semaphore:  # limits concurrent projects
            result = await self.workflow.run_full_pipeline(project_id)
            await self._notify_completion(project_id, result)
    except Exception as e:
        await self._handle_project_failure(project_id, e)
```

The semaphore limits concurrent projects to prevent resource exhaustion. If you're running on a small VPS, you might limit to 3-5 concurrent projects. On a larger server, 20-50.

### Storage isolation

Each project's artifacts are stored in a dedicated directory:

```
/data/projects/{project_id}/
├── manuscript.md
├── editorial_report.json
├── cover_brief.json
├── epub/
│   └── book.epub
├── pdf/
│   └── book.pdf
└── metadata.json
```

This prevents filename collisions and makes cleanup straightforward — delete the directory, and the project's artifacts are gone.

## Performance optimisation

### Caching

Expensive operations are cached to avoid redundant work:

```python
class ResearchCache:
    def __init__(self, ttl: int = 3600):
        self.ttl = ttl
        self.cache: dict[str, CacheEntry] = {}
    
    async def get_or_fetch(self, key: str, fetch_fn) -> Any:
        if key in self.cache and not self.cache[key].expired():
            return self.cache[key].data
        
        data = await fetch_fn()
        self.cache[key] = CacheEntry(data, ttl=self.ttl)
        return data
```

Market research data is cached for 24 hours. If two projects target the same niche, the second project reuses the first's research instead of re-fetching.

### Connection pooling

Database and API connections are pooled to avoid the overhead of establishing new connections:

```python
from sqlalchemy.pool import QueuePool

engine = create_engine(
    DATABASE_URL,
    poolclass=QueuePool,
    pool_size=10,
    max_overflow=20,
    pool_timeout=30
)
```

### Lazy loading

Large artifacts (manuscripts, images) are loaded on demand, not kept in memory:

```python
class LazyArtifact:
    def __init__(self, project_id: str, artifact_name: str):
        self.project_id = project_id
        self.artifact_name = artifact_name
        self._data = None
    
    @property
    def data(self):
        if self._data is None:
            self._data = self._load_from_disk()
        return self._data
```
